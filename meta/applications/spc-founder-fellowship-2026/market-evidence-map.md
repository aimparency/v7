# Market evidence map: developer wedge vs real-world relationships

## Conclusion

Robin's Leipzig automation work, Herzog Records, and Wilde Möhre are credible
**learning channels for bounded organizational workflows**. Today they are not
evidence of customers, demand, or adoption for Aimparency's recommended initial
product: developer intent infrastructure.

Mentioning all three in the core SPC story would weaken it by switching buyers
and problem categories. Use them only to demonstrate disciplined real-world
discovery, or choose an organizational-workflow narrative and accept that it has
less direct product evidence.

## The central mismatch

| Dimension | Recommended product wedge | Current relationship experiments |
| --- | --- | --- |
| Buyer | Technical founder, maintainer, AI-native engineering team | Automation practitioner, record-label owner/operator, festival owner/operator |
| Work surface | Repository and coding-agent coordination | Client automation, release coordination, festival closeout |
| Existing proof | Running product and long repository use | Prepared hypotheses and relationship actions |
| External evidence | Public artifact, no third-party retention/payment | One sent invitation; two planned conversations; no workflow access/payment |
| Product motion | Install reusable infrastructure | Sell bounded diagnostic, then discover reusable primitives |
| Fastest falsification | Observe ten AI-native repositories | Secure one owner-authorized paid workflow diagnostic |

These can converge later around the same invariant—durable intent, explicit
human decisions, evidence-aware execution—but convergence is a hypothesis.

## Two coherent go-to-market choices

### Choice 1 — developer infrastructure first (recommended)

- Core application buyer: AI-native software teams.
- Core experiment: ten repository observations, three installs, one paid
  commitment or explicit budget rejection.
- Robin/Herzog/Wilde Möhre: omit from the main market claim; retain as adjacent
  learning channels about authority and real-world workflows.
- Advantage: strongest product evidence and cleanest application story.
- Risk: no named developer design partners are currently recorded.

### Choice 2 — paid organizational diagnostic first

- Core application buyer: owner-led organizations delegating a bounded workflow.
- Core experiment: one paid diagnostic with baseline, decision rights, stop
  conditions, reusable-product accounting, and a continuation decision.
- Robin/Herzog/Wilde Möhre: become the actual relationship-led entry paths.
- Advantage: potentially faster revenue and real-world authority evidence.
- Risk: looks like bespoke AI consulting and has a weaker causal link to the
  current repository-native product.

Do not present Choice 1 as the product and Choice 2 as existing traction. Pick a
primary learning path; describe the other as a deliberately bounded parallel
experiment only if space allows.

Use that sentence only if the application benefits from explicit candor about
the two-route test. A tighter application should choose one route.
